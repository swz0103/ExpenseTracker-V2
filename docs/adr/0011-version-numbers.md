# ADR-0011：版號只在發布時升，三碼各在什麼時候變

- 狀態：採用（2026-11-18）；2026-11-21 改寫：版號只在要發布時升，一次發布可以包含好幾個 PR
- 補充：ADR-0010（每個次版號留一份帳本與備份）

## 背景

最初的問題：0.17.0 之後 main 合併了 21 次，每次都自動發布，版號卻都是 0.17.0。使用者手上的「0.17.0」可能是其中任何一次，標籤與測試帳本都說不清是哪一個。

於是改成「每個會發布的 PR 都要升版」，結果走到另一頭：0.18.0～0.18.3 在兩天內發了四版，0.19.0 隔天又升。每個小整理都變成一個版本、一則更新通知、一份測試帳本。版號升得比使用者看得到的改變快。

## 決策

版號寫成 `主.次.修`（`apps/expense_tracker/pubspec.yaml` 的 `version`）。`+` 後面的組建號由 CI 填入執行序號，不必改。

### 什麼時候升：要發布時才升

- **PR 可以不升版。** 沒升版的 PR 照常驗證、合併，但不發布；等下一個升版的 PR 一起發。
- **要發布時才升版**，一次發布可以包含好幾個 PR。節奏建議是一批回饋或一週一次；資料出錯這類急件可以單獨發一個修訂版。
- **只升不降**：版號改了就一定比 main 高，否則驗證失敗（`integration-validation.yml`）。
- 一次發布有好幾種改變時，照最高的那碼升，而且**只升一次**（0.19.0 → 0.20.0，不會因為合了三個 PR 就變 0.22.0）；升了某一碼，後面的碼歸零。

### 第一碼：主版號

使用者的資料或手機跟不上時才升，也就是舊版 App 讀不了新版寫出的資料，或有人從此不能更新：

- 帳本或備份的格式改版，舊版 App 打不開（`recordVersion`、`RowStore.schema` 或 `LedgerBackup.version` 升版）。
- 加密方式改變，舊版 App 解不開。
- 最低支援的 Android 版本提高。
- 拿掉使用者在用的功能，或改變資料的意義。

1.0.0 之前第一碼固定是 0，遇到上面的情況改升第二碼，並在 CHANGELOG 寫明舊版讀不了。作者認為功能已經穩定、且一個月內沒有資料相關的問題回報時，升到 1.0.0。

### 第二碼：次版號

使用者看得到新的或不一樣的東西，舊資料照常可讀：新功能、新畫面或設定；畫面的樣子、排列、顏色明顯不同；算法、預設值、顯示的寫法改變；新增權限；資料多了舊版仍讀得懂的欄位。

### 第三碼：修訂號

使用者看不到刻意的改變：修 bug、效能與穩定性、整理程式、補測試、更新套件、錯字。

### 每個版號

- `whats_new.txt`（三行以內，給使用者看）與 CHANGELOG 一節。
- 次版號以上留一份它寫出的帳本與備份（ADR-0010）；修訂版不用。
- CI 第一次發布時打上標籤 `v<版號>` 並建立同名的 release，放 `ExpenseTracker-<版號>.apk`、`update.json` 與測試帳本；App 從 `releases/latest` 找更新（[android.md](../android.md)）。
- GitHub 上只留最新一版的 release 與標籤：新版公開後，舊的連同標籤刪掉。

### 例子

| 改了什麼 | 升哪一碼 |
| --- | --- |
| 只整理程式、補測試 | 不升，跟下一次發布一起 |
| 320 dp 手機上預算卡溢出，修好，想馬上給使用者 | 第三碼 |
| 新增「月結報表」頁 | 第二碼 |
| 一週內合了新頁面、兩個修正、一次整理，一起發 | 第二碼一次 |
| 備份格式從 v3 改成 v4，舊 App 讀不了 | 第一碼（1.0 前：第二碼，CHANGELOG 寫明） |

## 後果

- 使用者手上的版號仍對得到一個組建、一個標籤、一份測試帳本（次版號）。
- 版號只在使用者有東西可拿時才動；更新通知不再因為內部整理而跳出。
- 拿不準升哪一碼時取較高的那碼；拿不準要不要發布時，先不升，等下一批。
