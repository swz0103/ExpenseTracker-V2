# 2026-09-29 架構回查與整合驗證

範圍：`integration/v2-core`；只檢查 V2 私人專案。此紀錄區分已確認問題、風險與尚未通過的 gate，不把文件、原型或主機檢查等同正式產品驗收。

## 已確認

1. **帳本開啟的全量驗證成本（效能風險，高）**：`GenerationStore.current()` 原先在 `_recover()` 驗證目前世代後，再呼叫 `_inspect()` 對同一內容驗證第二次；本批已讓 `current()` 重用同一把鎖內的首次驗證結果。`withCurrent()` 原本即只有一次，目前仍會透過 Ledger 的 `LedgerPayload.inspect()` 與 `SnapshotCodec.capture()` 驗證並序列化整份權威資料。已記錄的 5,000 事件合成帳本在 Windows 主機重開約 105 秒、另一輪約 108 秒，詳見[前次量測](architecture-audit-2026-09-28.md#後續實測大量帳本的開啟驗證成本)；這些是修正前資料，尚無固定資料集的改善量測。保留 fail-closed，不略過完整性檢查。後續須分開量測密文完整性、邏輯歷史及序列化，再訂可驗證的快取失效或驗證時機，回歸損壞、升級、程序中斷與雙憑證還原。100k+ 目標尚未驗收。
2. **App 畫面狀態集中（維護與競爭風險，中）**：`prototypes/expense_preview/lib/main.dart` 目前約 2,448 行，單一狀態物件協調鎖定、帳本、草稿與多個業務畫面；拆出的 `part` 檔仍共享同一私有狀態。已有鎖定時延遲結果與備份路徑競爭的歷史修正，因此後續功能應先明確界定 session epoch 與狀態所有權；遇到可重現交錯再把該流程移到獨立協調層，不先全面改寫 UI。
3. **雲端檢查清單漂移（驗證缺口，中）**：舊 `Foundation probe` 的矩陣沒有 `packages/data_exchange`，兩份原 workflow 又只可手動觸發且預設分支沒有 workflow 檔案，無法直接對整合候選執行。新增的 `V2 integration validation` 在整合分支的 workflow 或本次跨平台測試檔變更時觸發，使用單一整合提交，依本機清單涵蓋架構、11 個業務套件、8 個資料／原型套件與 2 個 Flutter App。四個 Linux job 的 timeout 合計上限 68 分鐘，不含裝置測試。舊高成本 workflow 保持停用。
4. **測試平台路徑（已修正並重驗）**：首輪雲端資料保存組在交易子程序測試找到寫死 `.exe` 的路徑；同組其他資料保存測試通過。已讓該測試依執行平台選擇副檔名，Windows 主機重新建置 worker、分析與 11 項測試通過。這是測試路徑修正，並未改變交易提交程式；修正後整合提交的四組雲端檢查全部通過。

## 下一批技術處理

- 下次有新程式變更時，依影響範圍做主機回歸；需要雲端 gate 的整合批次另選固定提交與額度，不因一般推送自動耗費 Actions。
- 以帳本開啟性能為先，提出保留損壞偵測能力的分段驗證方案並做同一資料集量測；在此之前不放寬安全驗證。
- M2 預算進入保存與 App 流程時，保持 Ledger 為交易權威、預算為獨立版本化規則；檢查分類／Tag 歷史歸屬與備份範圍，避免 UI 直接讀寫 Ledger 私有資料。
