## 每批上傳核對

1. 修改與推送前確認工作目錄、origin 的 fetch／push URL 及 GitHub 身份仍是上述 V2 專案，並檢查是否有使用者未提交的變更。
2. 完成該批需要的驗證，提交程式、文件、必要 fixture、鎖定相依及可追溯驗證紀錄，推到指定 V2 功能分支；功能透過小型 PR 審查並記錄依賴。
3. 推送後比對本機 commit 與遠端 branch／PR 的完整 SHA。檢查工作目錄及尚未被 origin 分支涵蓋的提交，不能只看到 push 指令執行就宣稱全部上傳。
4. 排除認證、金鑰、真實帳本、同步來源、SDK、建置快取與測試暫存；必要驗證摘要和原始測量結果放入 `docs/test-results/`。可交付 APK 另按建置、簽章與來源版本規則管理，不把本機暫存全部送上 GitHub。
5. 上傳與合併 main 分開處理。main 保留既有驗收限制；功能分支已上傳，不表示 main 已包含該功能，也不代表尚未執行的雲端或實機 gate 通過。

## 加快方式與保留步驟

- 以一段完整使用流程為交付單位；同一功能所需的規則、保存、升級、備份、必要畫面與測試集中完成，內部小改動不必各自拆成新的 PR。
- 可獨立的檔案讀取、分析與不同套件檢查同時處理。Windows 同套件的原生 worker 建置和測試仍循序執行；大型資料測試依記憶體、CPU 與磁碟負載調整並行數，避免競爭拖慢整批。
- 修正、等待、批准及依賴順序保留。測試執行時可整理該功能文件或檢查互不影響的項目；不得同時改寫正在驗證的程式，再把舊結果當成新程式通過。
- 每批先做受影響回歸、正常／邊界／失敗／重試驗證；重要整合點完成完整主機清單與需要的大量資料、備份還原及升級測試。已通過且沒有相關變更的檢查不無故重跑，未跑的範圍明列。
- 回查既有模組的正確性、接口、重複實作、效能及維護成本，修正有證據的問題；避免為抽象化或增加測試數而擴大工作。
- 完成可審查功能並核對上傳後，仍有授權且無阻礙時，在同一輪直接接下一項，不把每次排程限成只能完成一個 PR。
- 持續保留資料不變量、加密及雙憑證還原、故障回滾、升級來源保留、架構邊界、必要 UI 驗收、文件、PR 與上傳核對。加速不降低 gate，也不以測試數或分支數代替可用功能進度。

Actions 仍依額度政策停用，需雲端 gate 的分支收斂暫緩。不以增加雲端執行、付費、接受新授權或操作手機換取速度。背景排程的啟用／暫停狀態與頻率保留使用者現有設定，不以工作效率調整為由擅自改動。
