# 同幣轉帳、來源手續費與可恢復送出

2026-09-28，依賴 [PR #53](https://github.com/swz0103/ExpenseTracker-V2/pull/53) 的共用日期輸入。對應 M1-03、[RC-03 Ledger](../architecture/architecture-baseline-v1.0-rc1.md#rc-03)、[RC-04 Money／FX](../architecture/architecture-baseline-v1.0-rc1.md#rc-04) 及 [Full Vision FV-047 結構化費用](../architecture/full-vision-baseline.md#fv-047)。這是 M1-03 的同幣部分，跨幣與實際匯率仍須接續；M1／M2／M3 未全部完成。

## 財務行為與介面

首頁提供「同幣轉帳」。來源及目的必須為同一工作區、不同 ID、相同幣別與精度的啟用帳戶。目的清單只列合法候選，使用者明確選擇；切換來源後，已不相容的目的選擇清空。沒有候選時提示建立另一個同幣帳戶。後端仍重新驗證雙方狀態、版本、幣別、日期與金額，不能只依賴 UI 篩選。

本金必須正數，來源手續費預設 0 且不得為負數。兩個欄位沿用精確十進位及計算器：原算式只保存於草稿，明確套用後才可提交；不把手動小數偷偷取位。來源總扣款 = 本金 + 手續費，目的增加本金；本金不列收入或消費，手續費獨立列支出。例如兩邊期初各 100，轉帳 20、費用 1.25，餘額為 78.75／120.00，收入 0、消費 1.25。

單一事件保存兩個 principal legs 與可選的來源 fee leg，共用原子 transaction、operation receipt 與 audit。任一帳戶驗證、金額溢位、寫入或容量檢查失敗，全部回滾。相同操作重送核對原命令，既有結果不再扣費。允許帳戶出現負餘額沿用既定帳戶規則，不新增未決議的禁止透支限制。

列表清楚標示「來源 → 目的」、日期、轉入本金、手續費支出與轉出合計。讀取接口保留來源 principal 的帶符號數字，另提供 destinationId 與 fee；頁面不再把 ordinal 0 當成整筆轉帳。查詢在既有主鍵上額外連接目的 leg，每頁單一查詢，不為每筆另開一次資料庫查詢。三個金額共用既有隱私文字與朗讀標籤，不在 subtitle 裸輸出金額。

目前轉帳不附分類、商家、Tag，也不提供沿用交易、修改、刪除或跨幣入口；傳入不支援的附加資料明確拒絕，不能忽略後當成成功。後續費用分類與跨幣需求須延伸契約及回歸。

## 草稿與失敗重試

沿用一個本機加密草稿槽。新的 `manual-transfer-v1` 保存來源／目的 ID、本金原文、費用原文與日期；舊收支 `manual-entry-v1` 編碼不變。仍使用現有 AES-GCM envelope、profile／generation／workspace 綁定，不將草稿混入可攜正式帳本。

送出前先保存凍結命令，包括同一事件 ID、operation ID、雙方帳戶版本、原幣與精度、本金及費用。送出後未收到回覆時，重啟透過 receipt 核對並恢復；提交前中斷則以同一命令繼續。凍結時不能修改欄位；只有證明未提交後才能回到編輯。草稿保留未完成或不合法文字，不能據此改變正式餘額。

匯出、還原及升級前仍須先處理草稿。舊版 V2 的未完成收支草稿不能被升級丟棄；使用者先回原版本完成或捨棄，再明確升級。

## 資料版本與安全升級

新 App 使用 schema 8／portable snapshot 7，manifest 增加 `session_transfers: 1`。財務表本來就有 multi-leg 能力，因此本次沒有新增一套轉帳私有表；提升版本是明確宣告新 App 可讀寫的財務子集，讓舊 App 不會開啟後僅顯示來源一邊。

已知升級路徑 `ledger-7-to-8-v1` 延續既有流程：捕捉來源、產生並讀回驗證密碼／救援雙憑證安全備份、建立新 generation、驗證所有財務與歷史關聯、原子發布。舊 DB／key 保留。重新執行會從最後已提交版本接續；其他來源變更使舊計畫失效。schema 3～6 仍逐段走原有已知路線，不跳過原安全備份。舊 reader 對 schema 8／snapshot 7 拒絕，不降版、不原地改寫、不接受任意未來版本。

新 flags 預設關閉，`transfersAware` 向下包含既有 merchants／tags／category references；來源檢查依物理版本開啟對應能力。低層 Ledger 的既有 transfer fixture 仍可在歷史原型格式驗證，不能把它冒稱舊 App 已支援轉帳。

這些都是 **V2 內部版本**；沒有讀取或搬入舊 App `com.wzet.app` 的帳本、儲存空間或金鑰。

## 容量與驗證

目前仍是 32 帳戶／5,000 事件（含期初）的有界工作階段，不宣稱最終 M3 容量。legs 表允許最多 3 × 事件上限，但會依工作區／事件檢查實際 leg 數；全體 50,000 rows、16 MiB 可攜 payload 及每 row byte cap 仍生效。完整語意驗證由 SnapshotCodec stage／capture 執行，容量 admission 不代替財務驗證。重送不因達上限失去原有含義。

本機驗證清單記錄完整 18 套件／723 項（新增 26 項），以及全量後提示修正的 13 項相關回歸；不重複加總，亦不冒稱提示修正後再次跑完全部 18 套件。範圍包括草稿編碼、雙帳戶與 fee、失敗回滾／重試、schema 7 → 8 真實程序中止、App 舊草稿升級阻擋、舊 reader 拒讀、清除原始 DB／keys 後雙憑證獨立還原、UI 與隱私、大量資料與全主機回歸。首次測試 fixture 漏接受保護 catalog，以及 SemanticsHandle 清理時機不符測試生命週期，皆修正後重驗；完整主機與最終回歸無失敗。回查另修正帳戶未選、同帳戶及負費用提示，避免沿用收支文案讓使用者誤解。

GitHub Actions 維持停用；手機、實際 Android Keystore／文件選擇／TalkBack 與平台還原 gate 待使用者回來。不得因本機通過宣稱雲端或實機已完成。

大量資料結果：5,000 事件（2 期初、1 原有收入、4,997 同幣轉帳）、4,998 次重送、28,748 rows、8,331,009 bytes snapshot。從 schema 7 升級後持續使用，達事件上限的新交易被拒絕且完整 snapshot 不變。獨立計算來源／目的餘額為 10,203／3,003 最小單位，費用合計 7,494，沒有把本金當收入或消費。刪除來源資料與所有原 key 後，密碼及救援各用乾淨 profile 還原，核對完整 snapshot、重開及每條路徑 5,000 筆無遺漏／重複的分頁。此次主機端總耗時約 307 秒，包含填入、重送、備份、清空、兩次還原與完整比對，不能當成實機單筆操作延遲或 100k 能力。
