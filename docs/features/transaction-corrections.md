## 使用者流程與財務語意

- 使用者從一筆已入帳的收入、支出或同／跨幣轉帳發起「更正交易」，查看原值及擬替代的新值，輸入原因並明確確認。期初餘額、退款、撤銷本身不走此通用更正流程。
- 更正是**原交易的完整反向事件＋新的替代事件**；原交易與其歸屬、修訂、收據、audit 永遠留存。原交易的反向事件以原交易的 business date 入帳，將原月份與所有相關帳戶的原 legs 精確抵銷；替代事件以使用者確認的新 business date 入帳。因此目前報表可反映更正後的日期／金額，活動仍揭露實際操作時間和原始事實。
- 替代事件第一批保持相同交易種類，可修改帳戶、金額、日期、分類、Tag、商家及轉帳實收／費用。轉換收入↔支出、分拆轉換或信用卡／投資的業務更正另走明確流程；不以偽裝成同類更正繞過其規則。
- 原交易若已有退款、撤銷或更正，拒絕再次通用更正；不自動級聯修改後續依賴。替代交易其後的退款／撤銷按新事件的限制處理。每筆原交易至多一筆替代關聯。

## 命令與保存邊界

- 更正命令包含原事件 ID、原財務事實／歸屬的凍結快照、反向與替代事件的獨立 ID／operation ID、原因及替代輸入。兩個 operation ID 必須彼此不同且都不等於原入帳 operation。
- 同一個 SQLite transaction 完成依賴與版本檢查、完整反向事件、替代事件、歸屬、兩筆 operation receipt／audit 及唯一關聯。任何階段失敗，兩筆事件和關聯全部回滾。重送必須比對兩個收據和關聯，完整相同才回傳已提交；不能把其中一筆原先單獨存在的事件誤認為成功。
- 保存與可攜備份應升至新 reader 能力／schema／snapshot 版本，明確保存原→反向→替代的鏈。還原須雙向驗證來源、唯一性、完整反向 legs、替代事件、兩個 receipt／audit、所有歸屬及版本；孤兒、重複、竄改、未知格式皆拒絕。
- 沿用單一加密草稿槽及 staged generation upgrade。草稿在確認前保存，提交後中斷須以**整組**收據與關聯精確證明成功才清除。升級前安全副本需由密碼與救援金鑰各自驗證，舊 DB／key 保留。
- 一般文字備註仍用獨立 revision；更正前原備註保留在原交易。替代交易不暗中繼承備註或 external ID。一般 tombstone 與錯誤輸入的刪除政策屬下一個流程，不在本批暗改有效集合。

## 驗收與回查

- 驗證單／跨幣、三個轉帳 legs、fee、分類與當時歸屬、跨月日期、邊界金額、帳戶版本與生命週期；獨立重算更正前後各帳戶餘額和期間收支，確保不把原交易排除後再計一次反向事件。
- 驗證已有退款／撤銷、錯誤工作區、重複事件或 operation、同時競爭更正、容量不足、每個寫入 checkpoint 的回滾、原本成功後的重播及碰撞拒絕。
- 驗證真實 V2 舊版升級中斷、損壞／缺漏備份拒絕、密碼及救援兩路來源刪除後乾淨還原，並回查備註、退款、撤銷與 Activity 分頁沒有回歸。
- UI 需在隱私、背景鎖定、草稿重啟、大字體／窄螢幕維持安全與可讀；雲端、實機和正式發布 gate 分開列證據。功能通過前不在正式 UI 顯示，不能把本文件視為完成聲明。
