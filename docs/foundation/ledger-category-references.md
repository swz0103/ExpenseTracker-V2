# 交易分類引用與歷史還原

本批延續 [Categories 工作階段](category-session.md)，完成收入／支出分類分攤的業務契約、原子保存及獨立加密暫存還原。對應[實作安排的 M1-02](../delivery/implementation-plan.md)；屬於可測試的底層能力，正式帳本世代升級、session 容量政策及 UI 接入仍為下一批。

## 引用與金額

`Allocation` 保留分類公開 ID、精確金額，新增正整數 `expectedCategoryVersion`。既有未指定版本的 Domain 提案可保留，但持久化新引用必須帶版本；不默默假設版本 1。收入與支出共用分攤驗證：幣別一致、每份為正、分類 ID 不重複、總額精確等於收入或支出。

分攤僅表達分類歸屬，不新增資金 leg。100 期初、收入 20、支出 10（飲食 6＋交通 4），餘額仍為 110。期初與轉帳本金沒有分類分攤入口；轉帳費用的進階歸屬保留後續範圍。

同一 SQLite transaction 內，先透過 Categories 目前狀態驗證 workspace、收入／支出類型、預期版本與可選狀態，再保存事件、資金 legs、分攤、receipt 與 Audit。分類在讀取後被其他命令修改時，入帳必須通過版本檢查；交易和分類修改依 transaction 序列化。

## 為何保留分類歷史位置

每筆分攤保存 `category_version` 與 `category_sequence`。前者是選定分類的版本；後者是這次交易寫入時，該 workspace 已提交的分類變更序號。同一事件的所有分攤必須使用同一歷史位置。它是 metadata 順序，不是交易日期，也不靠裝置時鐘決定先後。

因此分類之後改名、封存或合併，都不改寫舊交易的原 ID、金額或引用版本。還原時依分類歷史重放到指定位置，核對當時是否存在、可選、類型及版本是否相同；不以今天已封存的狀態否定當時合法的入帳。原分類與合併後的顯示身份仍由 Categories 的歷史解析提供。

所有事件共用一次分類歷史重放；用 workspace／sequence 索引檢查待驗證引用，沒有為每筆交易重新掃完整歷史。Categories 原有每一步 catalog 驗證成本仍存在，沒有宣稱任意 metadata 歷史長度都線性。

## 格式與相容性

- 明確 `categoryReferences: true` 使用 **財務 schema 5／snapshot 4／ledger module 3**，包含 Categories 及本機世代身份。
- `allocations` 增加版本與歷史序號兩欄，並有正數檢查及 workspace 範圍的分類／歷史外鍵；其餘權威表格式保持原規則。
- 帶引用的入帳使用結構化 `posting-v2` receipt，保存 legs 與分攤 ID／預期版本／Money。未帶分攤仍使用原 `posting-v1`，保留既有 receipt 的精確重送身份。
- 自動取得的歷史序號不參與命令輸入去重。分類後續改動後重送原交易，仍回傳已完成結果；改用不同版本或分攤內容重送同 operation 則拒絕。
- schema 2／3／4 預設 reader／writer 行為保留。舊 reader 拒絕新格式，新 reader 也不直接就地打開舊檔升級；使用另建的 stage。
- 已知舊快照可轉換其空分攤表。舊版從未支援可驗證的持久分攤，若舊 snapshot 出現分攤列，拒絕而不猜測版本或歷史位置。

完整還原除既有財務不變量外，會檢查分攤正數與加總、分類存在與所屬 workspace、歷史版本及可選性、同一事件的歷史位置一致、分攤與 receipt 的 ID／版本／Money 完全相符，以及 module／表／欄位形狀。任何缺列或未知格式都拒絕。外鍵可先於語意驗證拒絕跨 workspace 偽造；錯誤仍必須保留來源。

## 驗證範圍

新案例包含收入分攤的不變性與精確總額、跨帳本／過期／類型錯誤／缺少版本拒絕、20 次重送、分類修改與入帳競爭，以及 event、leg、allocation、receipt、Audit 五處提交前故障的全量回滾。

還原測試保留分類改名、合併及封存後的交易，並注入金額、引用版本、分類、歷史位置、receipt、module、欄位及 workspace 異常。schema 4 轉換、禁止就地開啟及 allocation 階段中止均檢查來源不變。

回查另重現來源資料表失去主鍵限制後的問題：重複分攤在驗證索引中被覆蓋，可能匯出無法還原的備份。已加入明確的重複 ID 拒絕與實際損壞 schema 案例；先確認舊檢查會錯誤接受，再補強並回歸快照及加密套件。共用合成資料也改為明確套件入口，避免測試以相對路徑繞過模組邊界；沒有放寬架構規則。

密碼與救援金鑰分別只提供給全新程序，來源 DB 先刪除，目標使用新隨機 DB key／binding；比較全部可攜資料及加密檔不含合成明文標記。這是**暫存還原驗證**，不等同已實作 schema 5 的正式 active generation 發布。

大量測試使用同一加密帳本：含期初共 5,000 事件、4,999 筆新增與 4,999 次重送，2,500 筆收入及 2,499 筆雙分類支出，共 7,498 分攤。分類之後合併／封存，再以密碼與救援各自還原，核對完整 bytes、獨立金額計算及原交易 replay。[原始結果](../test-results/2026-09-27/category-references-scale-2026-09-27.json)記錄 snapshot 7,751,582 bytes，預期餘額 2,511,000 minor units，全案例約 173.73 秒；同時有其他本機檢查，不能當作隔離效能或實機承諾。完整 14 套件共 464 項獨有本機案例通過，最後重複分攤修正另全量回歸快照及加密套件；[驗證清單](../test-results/2026-09-27/category-references-host-2026-09-27.json)保留執行範圍，整體 gate 以[工作進度](../work-progress.md)為準。

另保留[既有 schema 3 → 4 的大量回歸](../test-results/2026-09-27/category-references-legacy-regression-2026-09-27.json)：5,000 事件搭配 256 分類及 1,024 次 metadata 變更，核對安全備份、世代重試、舊來源保留與雙路完整還原。這是另一個帳本／另一個案例，不與新引用案例混算成單一帳本容量。

## 尚待接入

後續[分類引用世代升級與工作階段](ledger-reference-upgrade.md)已接上以下 Ledger 層工作；本節保留本批交付時的邊界，App／UI 與平台 gate 仍未完成。

`LedgerStore`／`LedgerSession` 和 App 目前仍支援原 schema 3／4 路徑，分類分攤的正式世代發布與 session 寫入容量預檢未接上；不能藉新低層開關直接在產品啟用。接續須完成已知 schema 4 → 5 的同鎖安全備份／轉換／發布、相容舊來源、含分攤資料的全域 bytes／列數保護及讀取接口，再接正式備份設定、升級流程與 UI。

既有 16 MiB／50,000 可攜列上限維持；本批大量測試不等於工作階段已承諾新容量。需要的 Android、OS 中止／斷電與真實磁碟滿驗證仍保留。依[CI 額度政策](../delivery/ci-budget-policy.md)採本機檢查，雲端未執行，手機未操作。
