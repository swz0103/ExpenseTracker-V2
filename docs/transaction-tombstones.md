## 有效集合與操作範圍

- 一般刪除只接受單筆正式收入、支出或轉帳，包括同幣與跨幣轉帳；原始 `events`、legs、歸屬、備註、收據與 audit 不刪除。獨立的 `event_tombstones` 記錄原事件及刪除 operation；原事件從**目前有效集合**退出，餘額、期間收支、分類與搜尋都只計入仍有效的事件。交易活動仍可查閱原事實與刪除時間。
- Tombstone 不建立反向財務事件。已有正式反向事件的原交易仍需計入原額，與該反向事件相抵；因此不能再對它做 tombstone，否則會雙重抵銷。退款、正式撤銷、更正或任何已建模的後續依賴都拒絕通用刪除，不能級聯移除。
- 期初餘額、退款、撤銷事件、已刪除事件、跨業務的信用卡／投資事件不走此入口；它們需要各自的更正或生命週期規則。文字備註修訂不阻止刪除，但保留於歷史。草稿未入帳，直接丟棄草稿不產生財務 tombstone。
- 首批不提供假裝無痕的短暫 Undo。日後若允許重新啟用，須以新的審計 operation 驗證期間依賴，不能移除舊 tombstone 或直接覆寫原交易。

## 命令、保存與查詢邊界

- 刪除命令凍結原事件 ID、完整原財務事實、原 operation、獨立刪除 operation 與原因。提交時在同一 SQLite transaction 重新讀取權威事件與所有依賴，逐欄比對凍結事實，寫入唯一 marker、operation receipt 及 audit；任一步失敗全部回滾。重送須比對 marker、收據、audit 與命令；相同回傳已提交，碰撞拒絕。
- 同一交易內更新或直接重讀受影響帳戶的有效餘額，不能保存一份與 Ledger 不一致的 current balance。所有現有讀取路徑，包括交易列表、活動、退款／撤銷／更正來源、帳戶餘額及未來報表，都必須明確區分歷史事實和有效集合，不能只在 UI 隱藏原交易。
- 新 reader、schema、加密 generation 與可攜 snapshot 要一同升版，明確保存 tombstone 關聯及其收據／audit。還原拒絕孤兒、重複、錯誤 operation、跨 workspace、已依賴事件及錯誤資料版本；可重建的有效餘額須與乾淨還原一致。舊版升級沿用事前雙憑證驗證的安全備份與 staged generation，故障時維持舊資料可讀。
- 有效集合的容量以權威 marker、收據與 audit 一起預檢；已刪除歷史仍佔備份容量，不能用刪除繞過 5,000 事件及可攜檔限制。App 預設功能在主機、雲端與實機各自 gate 前保持隱藏。

## 驗收案例

- 驗證收入、支出、拆分、同幣／跨幣轉帳、費用與跨月日期：刪除前後各帳戶餘額和期間收支由有效 Ledger 獨立重建；歷史活動仍能顯示原事件與原因。
- 驗證原交易已有退款／撤銷／更正、錯誤 workspace、期初餘額、重複刪除、operation 碰撞、並行競爭及容量不足全部拒絕，快照不變。
- 驗證每個寫入 checkpoint 回滾、重送精確比對、舊資料升級中斷、密碼與救援金鑰各自於刪除來源 DB／金鑰後乾淨還原；損壞或缺漏 marker 的備份拒絕。
- 簡潔 UI 要預覽受影響帳戶與日期、二次確認、尊重隱私與鎖定狀態，窄螢幕／大字體可讀。雲端與實機未通過前，不宣稱正式功能完成。
